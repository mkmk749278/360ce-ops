Containers — what is running on the box

{% include "_system_verdict.html" %}

Every container in both stacks, from Docker's own state rather than inferred from data a still-warm cache is serving. That is the one check that cannot be fooled by stale data, because it reads none: on 2026-07-27 an interrupted compose recreate left the engine Exited (137) and redis Created for two and a half hours while every other detector read engine health out of a frozen api cache.

Read Uptime against its stack-mates, not Restarts

The engine carries autoheal=true and a healthcheck that tests work — scanner-heartbeat freshness, not just process-up — so a wedged scan loop makes the container unhealthy and the autoheal sidecar restarts it. That is the design and it is usually right. But a restart takes every snapshot:* key past its TTL, which empties this dashboard — so a loop of restarts is the thing to catch.

The restart counter cannot catch it, and this page said otherwise for an hour. Docker's RestartCount counts restarts made by the container's restart policy. Autoheal issues a manual restart, which does not increment it; a compose recreate builds a new container, which starts the count over. On the first live read of this page the engine had plainly restarted on its own — up 1h48m beside an api, signing and watchdog all up 5h16m — and its count read 0.

Uptime is blind to neither, because a restart always resets it. What uptime alone cannot say is whether the whole stack went down together — an ordinary deploy — or one container went down by itself. So the stack's start times are grouped: the largest group is the last deploy, and anything younger than it came back afterwards on its own — badged restarted alone. That badge appearing twice in a row on the engine is the autoheal loop. Containers older than the deploy cohort are not flagged: redis and autoheal have been up for weeks because nothing changed under them, which is history rather than an event. The first cut of this rule flagged them, and reading this page an hour after shipping it is what caught that. RestartCount stays in the table as what it honestly is — the policy-restart count — rather than as the headline.

Measured inside the engine container and published; this dashboard runs on a different cgroup and a reading taken here would describe this web process under the engine's name. A raw percentage alone answers nothing — 221% of a 250% quota is a process at its ceiling whose scan loop cannot meet its deadline however well it is written, while 221% of an uncapped 4-core box is a busy machine with a core to spare. This figure and the CPU column in the table above are two different measurements and will not match. That column is docker stats --no-stream: one instantaneous sample of roughly a second, taken while the page loads, and a scan cycle is bursty — it routinely reads 1.5–2× this one. Neither is wrong and neither is "the" CPU reading. The memory figures come from the same cgroup and do agree, which is what confirms both are reading this container rather than another.
