unknown is not up

A link ops could not measure gets its own badge and is never counted as passing. “We could not ask” and “we asked and it is fine” have different next moves, and a check that renders green when it did not run is worse than no check at all, because it is a claim. This table renders whether or not anything failed, for the same reason — a row that appears only when it trips teaches you its absence means “fine”, when it equally means the check stopped running.

Scan cycle the number the healthcheck kills on

The scanner touches its heartbeat file once, at the end of a cycle, and healthcheck.py fails when that file goes stale. Three consecutive failures flip the container unhealthy and the autoheal sidecar restarts it — which expires every snapshot:* key, so the dashboard stops answering and the app feed reads empty. Cycle wall-time is heartbeat age, and until 2026-08-19 it was computed every cycle and rendered nowhere: measured at 9.2s to 402.5s against a 15s target, with a restart inside the measurement window and docker's RestartCount still reading 0.

Read “Cycle in flight” and “Heartbeat age” before any counter below them. Every other number on this card records a cycle at completion, and healthcheck.py kills the container on heartbeat age — which the scanner touches once per completed cycle. So a cycle hung past the deadline appears in none of “past the deadline”, “worst this boot” or “last cycle”. On 2026-08-19 this card read 0 past the deadline, last cycle 20.76s while autoheal was restarting the engine on a failing streak of 3. A measurement that can only see finished work cannot see the work that is killing you.

“Concurrent scans” beside “Executor workers” is the queueing ratio: each scan awaits the pool, so a limit far above the worker count means the surplus is waiting, and that wait is what the stage breakdown reports as indicators wall-time rather than as anything named “waiting”.

Both bounds come from the engine, never from ops. A staleness threshold invented here is what made /truth read STALE for 23 hours out of every 24. Boot warm-up is counted apart and kept out of the verdict: a cold start re-seeds every pair over REST and rebuilds the indicator caches, so its first cycles run long by construction (74.5s / 131.2s / 72.8s measured after a deploy, against a steady state of 8–47s) and healthcheck.py holds its own grace for exactly that. Folding them in would leave this card red for the whole life of a healthy boot, which is a dead instrument rather than a warning.

The cache key was the bar count, which stops changing once a bucket reaches its cap — so a full bucket's indicators froze while its bars kept arriving. Frozen values avoided is how much that was actually happening; hits at the bar cap is its denominator. Undatable at the cap is a different state and never pooled with either: those buckets carry no bar timestamps, so they are recomputed every cycle — correct, but expensive, and the fix is a bucket re-seed rather than anything in the cache.

The monitoring agent — the process whose death is silent

A dead pager sends no message, so on Alerts “nothing is wrong” and “nothing is watching” render identically. The agent stamps what it just did after every cycle; this reads that stamp. Its healthchecks.io dead-man's switch is deliberately not pinged on a cycle that had failures, so on that channel a degraded agent and a dead one share a symptom too — which is why this carries cycle_ok separately from freshness.
